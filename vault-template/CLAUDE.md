# Vault schema

The rules every agent follows when it reads or writes this vault. Short on
purpose. The full contract is the `vault` CLI.

## Who writes

- Only the orchestrator writes, through
  `node ~/.claude/skills/dispatch-plan/vault.mjs`. Never with an editor.
- The reviewer only reads. It may run `boot` and read vault files. It never
  runs a write command.
- Workers never touch the vault. The CLI refuses every command when
  `PI_PLAN_DISPATCH_WORKER=1` is set, and the dispatcher denies any tool call
  whose path is inside the vault.

## Note types

Every note has `type`, `created` and `updated` (`YYYY-MM-DD`). Basenames match
`[a-z0-9-]+` and are unique across the whole vault, not just the type folder.

| Type | Basename | Required properties |
|---|---|---|
| `plan` | `<slug(plan-id)>` | `trace`, `round`, `repo`, `status` |
| `run` | `<slug(plan-id)>-run` | `trace`, `repo`, `status`, `gate`; optional `plan` (wikilink) |
| `finding` | `<trace>-f-<first 8 hex of sha1(fingerprint)>` | `trace`, `repo`, `severity`, `fingerprint`, `source`, `status` |
| `decision` | `decision-<slug(project)>-<slug(title)>` | `project`, `repo` |
| `lesson` | `lesson-<slug(project)>-<slug(title)>` | `project`, `repo` |
| `project` | `project-<slug(name)>` | `repos` (list of slugs) |
| `codebase` | `codebase-<slug(owner)>-<slug(name)>` | `repo`, `commit`, `graphify_version` |

`slug(s)` is lowercase, each run of non-alphanumerics becomes `-`, the `-` ends
are trimmed, and the result is cut to 60 characters. It applies to every
variable part of a basename.

A `plan` note is the archive copy of a plan's text, so it exists only for a
`full` repo. A `run` note is the digest of one run. Both are written once,
after the run, with their final state.

`repo` is a `host/owner/name` slug, or `-` for a general decision or lesson. A
general note is held to the `meta` body rules and to the `none` rule.

`fingerprint` is `<repo slug>:<repo-relative file or ->:<slug(title)>`. The same
fingerprint in two different traces is a repeat, and the repeat rate is what
`stats` reports.

## Vocabularies

| Property | Values |
|---|---|
| `status` on `plan`, `run` | `done`, `failed` |
| `gate` on `run` | `pass`, `fail` |
| `status` on `finding` | `open`, `closed` |
| `source` on `finding` | `plan-audit`, `auditor`, `pair`, `security`, `gate` |
| `severity` on `finding` | `blocker`, `major`, `minor`, or the dispatcher's `error`, `warn`, `info`, stored as given |

A plan rejected by preflight, and a run whose gate failed, are `failed`.

A finding stays `open` until a later fix round of the same trace passes the
gate; the orchestrator closes it then. The user may close one by editing it.

## Privacy

`repos.json` holds the allowlist: one entry per repo, with a mode. The mode
that governs a note is the mode of the repo the note names.

| Mode | What it allows |
|---|---|
| `none` | no note naming the repo. No note body, log text, `project.repos` entry or commit summary may contain the slug or the `owner/name`. |
| `meta` | `run`, `decision` and `lesson` only. Run bodies are generated by the CLI from `--set` fields. A `decision` or `lesson` body may hold no fenced code block and no tracked file path of that repo. |
| `full` | every note type, subject to `lint`. |

Unlisted repos, repos with no slug, and a missing or malformed `repos.json`
are `none`. The CLI fails closed in every command, reads included.

Never write the slug of a `none` repo into a note, a log line or a commit
summary, not even to say it is hidden.

## Boot set

At session start the orchestrator runs `sync pull`, then `boot`. `boot` prints,
in this order:

1. `CLAUDE.md`, always, whole.
2. The `project` note for the current repo.
3. The `open` findings of that repo, one item each, severity descending, then
   newest first.
4. The tail of `log.md`, the last 20 lines.
5. A fresh index, computed and printed, not written.

The budget is `boot_budget_tokens` in `harness.json`, counted as characters
divided by 4, and applies to everything after `CLAUDE.md`. Items are whole or
absent. When the budget runs out, items are dropped from the end and
`[truncated: <n> items]` says how many.

`boot` writes nothing, so the reviewer's `boot` is a pure read.

## Writing rules

- One fact per note. Link liberally: `[[basename]]` for a note, with a heading
  or an alias when the text needs it.
- Never an absolute path, never a secret. Name a repo by its slug and, where it
  matters, a commit.
- Cite the trace. Every note from a run carries its `trace`.
- Prefer a `decision` or a `lesson` only when the fact outlives the trace.
- `index.md` is generated and untracked. `log.md` is append-only and merged
  with `merge=union`, so append one line at a time and never rewrite it.
- Use the `obsidian-markdown` skill when you write or edit note text yourself:
  properties, wikilinks, callouts, embeds. Use the `obsidian-bases` skill when
  you write or edit a `.base` view in `templates/`. The CLI never depends on a
  view.
- Never write to the user's personal vault. This vault is the only one.
- Never run `graphify install --project` or `graphify hook install` in a
  project repo: both write instruction files or hooks into it.
